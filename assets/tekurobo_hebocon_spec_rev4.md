# テクロボくん ヘボコン出場版 制御ソフトウェア スペックシート

## 0. このドキュメントについて

本ドキュメントは、ものづくりサークル「TECH✩TECH」のマスコットキャラクター「テクロボくん」を模したロボットの、**ヘボコン（ヘボいロボコン）出場用・暫定版制御ソフトウェア**の仕様書である。Claude Codeによる実装作業の指示書として使用する。

将来的にはSTT/Gemini API/TTSによる音声対話、カメラ入力、有機的なフェイシャル演出を備えたイベント交流用ロボットへ拡張する計画があるが、**本仕様書はその最終形ではなく、大会出場に必要な最小限の機能に絞った暫定版を対象とする**。将来拡張を見据えたアーキテクチャ上の配慮は行うが、未実装機能（音声認識、対話AI、リアルタイムTTS、カメラ）の実装はスコープ外とする。

### 0.1 リポジトリ情報

- リポジトリ名：`tekurobokun-lite`
- URL：https://github.com/nid-techtech/tekurobokun-lite
- 「テクロボくん」の略称は `tcrb`。CADファイル等の関連ファイルには `tcrb` プレフィックスを付与する命名規則を踏襲する（ソフトウェア内で新規に生成するアセット・設定ファイル等も同様の命名規則に倣うことを推奨）。

## 1. スコープ

### 1.1 今回実装する機能
- p5.jsによるフェイシャル表示（アイドル時のまばたき・きょろきょろ＋簡易的な感情表現）
- バーコードリーダー（USB HIDキーボードとして認識）による走行モード制御（前進／後退／左超信地旋回／右超信地旋回／停止）
- あらかじめ収録した発話音声ファイル（koeiroink想定）の再生
- 音声再生の出力振幅に連動した口パク（フェイシャル）
- Arduino経由でのモーター駆動（TB6612FNG + タミヤ デュアルギアボックス）
- オフライン環境での安定動作
- 弱いCPU（Core m7-7Y25）でもハングしない軽量動作

### 1.2 今回実装しない機能（将来拡張・スコープ外）
- Google STT / Gemini API による音声対話
- リアルタイムTTS
- Webカメラ入力（筐体に固定用の穴のみ存在、ハードウェア未接続）
- 「30cm前進して」のような音声コマンドによる距離・角度指定制御
- 発話内容に応じた高度な感情表現ロジック（今回は再生音声ファイルに紐づく簡易表現のみ）

## 3. 入力デバイス仕様：バーコードリーダー

- バーコードリーダーはUSB HIDキーボードとしてPCに認識される（ドライバ不要、標準キーボード入力として扱える）。
- 特定のバーコードをスキャンすると、対応するASCIIキャラクタのキー入力（keydown→keyup）が送出される。
- 使用するキーと用途は以下の3系統に分かれる。それぞれ独立した機能であり、キー入力のディスパッチ先が異なる（9節のアーキテクチャ参照）。

| キー系統 | キー | 用途 | 詳細 |
|---|---|---|---|
| 走行制御 | `w` `s` `a` `d` `r` | 走行モードの状態遷移 | 4節参照 |
| 音声再生 | `1`〜`9` `0` | 発話音声スロットの再生トリガー | 6節参照 |
| デバッグ | `/` | デバッグモードのON/OFF切り替え | 8節参照 |

- **重要**：走行制御キー（`w/s/a/d/r`）は keydown イベントのみを走行モード遷移のトリガーとして扱い、**keyupイベントは無視する**。通常のラジコン操作（押している間だけ動く）とは逆の設計であることに注意。
- 音声再生キー（数字キー）・デバッグキー（`/`）も同様にkeydownのみをトリガーとする。
- 上記以外のキー入力は無視する。

## 4. 走行モード：状態遷移仕様

走行制御はステートマシンとして実装する。状態は以下の5種類。

- `STOP`
- `FORWARD`
- `BACKWARD`
- `TURN_L`（左超信地旋回）
- `TURN_R`（右超信地旋回）

### 4.1 状態遷移表

| 現在の状態 \ 入力 | `w` | `s` | `a` | `d` | `r` |
|---|---|---|---|---|---|
| `STOP` | → `FORWARD` | → `BACKWARD` | → `TURN_L` | → `TURN_R` | 無視 |
| `FORWARD` | 無視 | → `BACKWARD` | → `TURN_L` | → `TURN_R` | → `STOP` |
| `BACKWARD` | → `FORWARD` | 無視 | → `TURN_L` | → `TURN_R` | → `STOP` |
| `TURN_L` | → `FORWARD` | → `BACKWARD` | 無視 | → `TURN_R` | → `STOP` |
| `TURN_R` | → `FORWARD` | → `BACKWARD` | → `TURN_L` | 無視 | → `STOP` |

- 現在の状態と同じ入力は、ガード節で明示的に弾き、何も処理しない（無意味な同一状態への再遷移処理は書かない）。
- 状態が変化した場合、直ちに対応するモーターコマンドを1回送信し、以後はハートビート（4.3節参照）で同一コマンドを送信し続ける。

### 4.2 各状態でのモーターコマンド（`"L,R\n"` 形式、値は -100〜100）

| 状態 | L（左トラック） | R（右トラック） |
|---|---|---|
| `STOP` | 0 | 0 |
| `FORWARD` | +F | +F |
| `BACKWARD` | -F | -F |
| `TURN_L` | -T | +T |
| `TURN_R` | +T | -T |

F（直進速度）・T（旋回速度）は実機調整パラメータとして設定ファイル等に外だしし、コード中にハードコードしない。

### 4.3 安全機構：通信タイムアウトとハートビート（新規要件）

現行のArduinoスケッチ（`dualmotor_arduino.ino`）は、一度モーターに速度を与えると次のコマンドを受信するまでその状態を保持し続ける。シリアル通信の切断やアプリ側のフリーズが発生した場合、モーターが停止せず走行し続ける危険がある。ヘボコンという競技特性上、これは安全上のリスクとして対処が必要。

**対応方針（Arduino側・PC側の両方を変更する）：**

- **Arduino側**：`loop()` 内で最後にコマンドを受信した時刻を記録し、一定時間（暫定値：200ms、実機調整可）新しいコマンドを受信しなかった場合、自動的に `stopMotors()` を呼び出す。
- **PCアプリ側**：現在の走行状態がSTOP以外の間、一定周期（暫定値：80ms、実機調整可）で現在の状態に対応するコマンドをハートビートとして送信し続ける。状態が変化した際は即座に新コマンドを送信し、以後はそのコマンドでハートビートを継続する。

この2つは必ずセットで実装する。タイムアウトのみ追加すると通常動作中に誤停止し、ハートビートのみ追加すると根本的な安全性が向上しない。

## 5. Arduino通信プロトコル

- ボーレート：115200bps（既存スケッチと同一）
- コマンド形式：`"L,R\n"`（例：`"50,-30\n"`）。L・Rはそれぞれ -100〜100 の整数。
- 既存のピン配置・TB6612FNG制御ロジック（`setMotors()`, `stopMotors()`）はそのまま流用する。
- 上記4.3節のタイムアウト機構をArduinoスケッチに追加する（唯一のファームウェア変更点）。

### 5.1 ピン配置（既存流用・変更なし）

| Arduinoピン | TB6612FNG | 役割 |
|---|---|---|
| D3 | STBY | 常時HIGH固定 |
| D4 | AIN1 | 左モーター方向 |
| D5 | AIN2 | 左モーター方向 |
| D9 | PWMA | 左モーター速度 |
| D6 | BIN1 | 右モーター方向 |
| D7 | BIN2 | 右モーター方向 |
| D10 | PWMB | 右モーター速度 |

## 6. 音声再生仕様

### 6.1 概要

- 発話音声はkoeiroinkで事前収録したファイルを使用する。
- 音声デバイスはWindowsの**デフォルト出力デバイスをそのまま使用**する。アプリ内で明示的なデバイス選択UIは設けない。ただし将来デバイス選択が必要になった場合に備え、デバイス解決処理は`AudioPlayer`モジュール内の1箇所に閉じ込め、他のロジックに波及しないようにする。
- 再生時、出力音声の振幅（RMS等）を解析し、その値をフェイシャルの口の開閉度にリアルタイムで反映する（口パク）。この振幅解析パイプラインは、後述のエラー音声再生時にも同様に適用する（特別扱いしない）。

### 6.2 再生スロット方式

- 音声は**最大10個のスロット**（1〜9、0の計10キー、キー`0`は10番目のスロットに対応）に登録する。
- 対応する数字キー（バーコード経由）のkeydownを検知すると、そのスロット番号に音声が登録されていれば再生する。
- スロットが空（未登録）の場合は、**専用のエラー音声**を再生する。エラー音声も通常の発話音声と同様にフェイシャル（口パク）に連動する。
- 音声ファイルとスロット番号の対応、および各スロットのキャプション文字列（8節のデバッグHUDで字幕表示に使う）は、設定ファイル等で外部管理し、コードにハードコードしない。
- 再生中に別のスロットがトリガーされた場合は、再生中の音声を即座に打ち切り、7.6節の読み込み中表示を暫定1秒程度挟んでから新しい音声の再生を開始する。これは実際の処理待ちではなく、音声が唐突に切り替わる違和感を抑えるための演出上のインターバルである。
- 音声ファイルの再生トリガー方法（キー割り当て等）は別途定義する。

## 7. フェイシャル表示仕様

### 7.1 表示ウィンドウ

- 描画はp5.jsで行う。
- Windows上でフルスクリーンウィンドウを1枚起動し、解像度800×600（実機ディスプレイのネイティブ解像度と一致、4:3）でp5.jsキャンバスを描画する。拡大縮小・レターボックスは行わず、キャンバス＝ディスプレイ全面とする。

### 7.2 デザイン原則とディスプレイ表示の関係（重要）

テクロボくんの本来のフェイシャルデザイン（添付画像1）はほぼ正方形の構図であり、「二重円の目」×2＋「櫛形（5分割）の矩形の口」から構成される。一方、実機の筐体前面は約190mm角の正方形だが、その中央に埋め込まれるディスプレイの可視領域は約164×120mm（4:3）にとどまり、正方形デザイン全体をそのまま表示することはできない（添付スケッチ参照）。

- **本来のフェイシャルデザイン＝正方形の構図**であり、ディスプレイに表示されるのはその一部を4:3でクロップしたものという位置付けである。
- 筐体前面のディスプレイ周囲（ベゼル部分）は背景と同系色（白）のため、クロップの境界が視覚的に目立たない設計を想定している。
- 実装上は、目・口の座標を「4:3キャンバス（800×600）内に収まる構図」として直接設計してよい。正方形キャンバス上に描いてからクロップするような二段階の実装にする必要はない。ただし、目・口の**上下方向の配置に余裕を持たせ、正方形デザインの中心付近の要素（目・口）が4:3クロップの上下端で切れないようにする**ことを設計上の制約とする。
- 目・口の具体的な位置・サイズの最終決定は、実機のディスプレイとベゼルの見え方を確認しながら調整する（13節のパラメータ一覧に追加）。

### 7.3 描画要素

- **目**：二重の同心円が左右に1つずつ。線画（塗りつぶしなし、太めの黒線）。
- **口**：横長の矩形を縦線で5分割した櫛形。線画（塗りつぶしなし、太めの黒線）。
- いずれも単純な幾何形状のため、p5.jsでのプリミティブ描画（`circle()` / `line()` / `rect()` 等）で十分に再現可能。

### 7.4 アイドル時の挙動

無操作時にまばたき・きょろきょろ動作を行い、有機的な印象を出す。今回確定する仕様は「疑似乱数とインクリメントによって動作間隔にムラを持たせる」ことのみ。具体的な間隔・確率分布・可動範囲などのパラメータは実機での見た目調整が前提のため、コード内には決め打ちで埋め込まず、外部から調整可能な設定値としてまとめておく。

### 7.5 発話時の挙動

6節の音声振幅に連動した口の開閉。目などによる感情表現は今回は簡易的なもの（例：発話中は目の形を1パターン変化させる程度）にとどめ、複雑な感情推定ロジックは実装しない。

### 7.6 読み込み中表示

- 「目の丸がクルクル回る」アニメーションにより、現在何らかの処理中であることを示す表示を用意する（Windowsの起動アニメーションやYouTubeの読み込み中インジケーターのようなイメージ）。
- 今回の用途は、6.2節の音声スロット切り替え時（再生中の音声を打ち切ってから次の音声を再生するまでの間、暫定1秒程度）の視覚的なつなぎとして使用する。実際の処理待ちではなく、演出目的のインターバルである。
- `FacialEngine`の表示状態の一つ（例：`IDLE` / `SPEAKING` / `LOADING`）として実装し、アイドル・発話と同様に独立した状態として切り替えられるようにする。特定用途（音声スロット切り替え）に密結合させず、`AppOrchestrator`側から「読み込み中表示を開始／終了する」という汎用的な指示で制御できる設計とする。
- **将来の拡張を見据えた設計意図**：この読み込み中表示は、将来Gemini APIなどのLLM対話機能やクラウドTTSを統合した際の、ネットワーク応答待ち・TTS生成待ちの表示にもそのまま流用できることを意図している。今回のスコープでは音声スロット切り替え時の演出用途のみに使うが、`LOADING`状態を汎用的な「処理中」表示として設計しておくことで、将来的な用途追加時に`FacialEngine`側の変更を不要にする（開放閉鎖の原則）。

## 8. デバッグモード仕様

### 8.1 概要

開発・調整作業を効率化するため、デバッグモードを実装する。デバッグモードが有効な間、フェイシャル描画よりも手前のレイヤーに診断用HUD（Head-Up Display）をテキストでオーバーレイ表示する。

### 8.2 切り替え方法

- `/`キーのkeydownでON/OFFをトグルする（押すたびに反転）。
- 初期状態はOFFとする。

### 8.3 HUD表示内容

デバッグモードが有効な間、以下を常時テキスト表示する。

- **すべての可変パラメータの現在値**：11節の未確定パラメータ一覧に挙げた項目（走行速度F・T、Arduinoタイムアウト、ハートビート周期、アイドル挙動の各パラメータ、口パクしきい値、目・口の座標など）を含む、実行時に調整可能なパラメータをすべて表示する。パラメータが増減しても追随できるよう、`AppOrchestrator`または各モジュールが公開する読み取り専用のパラメータ一覧から動的に生成する（表示項目をHUD側にハードコードしない）。
- **発話内容のテキスト字幕**：現在再生中（あるいは直近に再生された）発話音声に対応するキャプション文字列を表示する（6.2節のスロットごとのキャプションを使用）。

### 8.4 設計上の注意

- HUDはあくまで診断用の重ね書き表示であり、フェイシャル本体の描画ロジック（`FacialEngine`）には影響を与えない。責務を分離した別モジュール（`DebugHUD`）として実装し、フェイシャルの描画とは独立に有効・無効を切り替えられるようにする。
- 大会本番中はOFFで運用する想定（表示が本来のフェイシャル演出を隠してしまうため）。

## 10. アーキテクチャ方針

将来の音声対話・カメラ拡張を見据え、責務ごとにモジュールを分離し、SOLID原則（特に単一責任・開放閉鎖・依存性逆転）を意識した構成とする。

| モジュール | 責務 | 備考 |
|---|---|---|
| `SerialLink`（Rust） | Arduinoとのシリアル通信のみ担当。ポート探索、コマンド送信、切断検知・再接続 | ハートビート送信のスケジューリングはこの層、または上位のOrchestratorが担う |
| `DriveStateMachine` | 4節の状態遷移ロジックを保持。入力キーを受け取り現在の走行状態を管理し、状態変化時にモーターコマンドを`SerialLink`に渡す | 状態遷移ロジックと入力ソース（バーコードリーダー）を分離しておくことで、将来音声コマンド等を追加してもこの層は変更不要にする |
| `InputSource`（インターフェース） | キー入力デバイスからの入力を抽象化 | 現状はバーコードリーダー（HIDキーボード）が唯一の実装だが、将来的な入力ソース追加に備えて抽象化しておく |
| `InputRouter` | keydownイベントを3節のキー系統（走行制御／音声再生／デバッグ）ごとに振り分け、対応するモジュールにディスパッチする | 走行・音声・デバッグの各モジュールがキーボードイベントを直接購読せず、単一の窓口を経由することで責務を分離する |
| `AudioSlotRegistry` | 6.2節のスロット番号↔音声ファイル・キャプションの対応を保持し、番号指定で音声とキャプションを解決する | 空スロットの判定・エラー音声への差し替えもここで行う |
| `AudioPlayer`（TypeScript） | 音声ファイル再生、Web Audio APIによる振幅解析、出力デバイス解決 | デバイス解決ロジックをこの中に閉じ込める（6節参照） |
| `FacialEngine`（p5.js） | 現在の表示状態（`IDLE` / `SPEAKING` / `LOADING` など）を受け取り描画するのみ | 音声解析や入力処理のロジックを持ち込まない（インターフェース分離）。`LOADING`（7.6節の読み込み中表示）は特定用途に依存しない汎用状態として実装し、将来の用途追加（LLM応答待ち等）でもこの層は変更不要にする |
| `DebugHUD` | デバッグモードのON/OFF状態を保持し、有効時に各モジュールが公開するパラメータ・現在のキャプションを読み取ってオーバーレイ描画する | `FacialEngine`とは独立したレイヤーとして実装し、フェイシャル描画ロジックに影響を与えない（8節参照） |
| `AppOrchestrator` | 上記モジュールを束ね、全体のイベントフローを制御 | 各モジュールは具体実装ではなく抽象（trait/interface）に依存させ、将来の音声対話モジュール追加時にOrchestrator層のみ差し替え可能にする |

## 11. 実装順序（フェーズ分け）

走行制御・フェイシャルとも、いきなり全体を結合せず、以下の順で段階的に実装・検証する。

### 11.1 走行制御

1. **バーコード入力→状態遷移のみ**：Arduino・シリアル通信を含めず、バーコードリーダーからのキー入力を受けて`DriveStateMachine`（4節）が正しく状態遷移することを確認する（状態はコンソールログやUI表示で確認できれば十分）。
2. **Arduino連携**：1.の状態遷移結果を`SerialLink`経由でArduinoに送信し、実際にモーターが駆動することを確認する。あわせて4.3節のタイムアウト・ハートビート機構を実装・検証する。

### 11.2 フェイシャル

1. **固定表示**：7節のデザインに基づき、目・口を固定パラメータで静止表示する。まずは正しい構図が800×600キャンバスに収まることを確認する。
2. **手動調整用モックアップ**：目の大きさ・位置、口の開閉度などの主要パラメータをスライダー等で手動操作できる開発用UIを用意し、実機のディスプレイ・ベゼルとの見え方を確認しながら値を追い込む。
3. **オーディオ連動・生物的動作の実装**：6節の音声振幅連動（口パく）と、7.4節のアイドル挙動（まばたき・きょろきょろ）を実装し、実機上でパラメータを最終調整する。

## 12. 非機能要件

- **オフライン動作**：本仕様範囲内の機能はすべてネットワーク接続なしで完結すること。
- **軽量動作**：Core m7-7Y25という非力なCPU上で、大会本番中にハングしないこと。不要な常時ポーリングや重い描画処理を避ける。
- **安全性**：10節・4.3節の通信タイムアウト＋ハートビート機構により、通信異常時に走行を確実に停止できること。
